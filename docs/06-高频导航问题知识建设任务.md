# 高频问题排查文档建设任务

## 1. 任务背景

应用工程师面对“到点精度异常”“导航运行参数异常”等现场问题时，经常只能看到结果现象，无法准确判断问题来自导航、定位、控制、地图、调度、车型配置还是其他模块。

当前困难的核心不只是缺少历史 Case，而是诊断所需的代码仓库不完整。只有单一仓库时，只能分析该仓库内部的触发条件；分析走到外部模块边界后，无法继续确认：

- 上游数据由哪个模块产生；
- 对应模块会记录哪些日志；
- 日志中哪些字段能够区分正常与异常；
- 哪个代码分支会造成当前现象；
- 不同版本的日志和行为是否发生变化。

因此，本任务的主线是：根据问题报表确定 Top 高频问题，补齐相关代码仓库，沿跨仓库调用链找到关键日志和判断字段，形成应用工程师可以执行的高频问题排查文档。

## 2. 核心判断

### 2.1 代码仓库解决什么问题

足够完整且版本匹配的代码仓库，可以建立：

```text
问题现象
→ 涉及的功能链路
→ 相关模块和仓库
→ 每个模块的关键输入、状态与输出
→ 失败分支和触发条件
→ 对应日志关键字及字段
→ 正常/异常判据
→ 下一步排查方向
```

代码用于回答“应该查什么、怎样判断、分析边界在哪里”。

### 2.2 代码仓库不能单独解决什么问题

代码可以证明某个原因在机制上可能发生，但不能单独证明某次现场事件就是这个原因。

确认一次实际事件的根因，仍需要与现场匹配的证据，例如：

- 问题发生时间；
- 机器人实际运行版本；
- 同期模块日志；
- 关键配置和运行参数；
- 必要的实时状态或复测结果。

因此，文档必须区分：

| 结论类型 | 可以由什么证明 |
| --- | --- |
| 代码触发条件 | 对应版本源码 |
| 建议检查的日志 | 日志语句及字段生成代码 |
| 现场已命中某分支 | 同期现场日志 |
| 现场根因 | 日志、版本、配置和复测形成的证据链 |
| 证据不足 | 缺少仓库、版本、日志或关键字段 |

### 2.3 报表解决什么问题

问题报表用于选题和确定优先级，不直接用于证明根因。报表应帮助回答：

- 哪些问题出现频率最高；
- 哪些问题影响项目或车辆最多；
- 哪些问题处理时间最长；
- 哪些问题反复出现；
- 哪些问题最值得优先建设排查文档。

## 3. 建设目标

第一阶段不追求完成整个 Diagnosis Agent，也不先建设 Case 数据集，而是形成可复用的高频问题排查知识。

目标包括：

1. 从现有问题报表中确定 Top 问题及建设顺序；
2. 为每个 Top 问题建立跨模块功能链路；
3. 列出完成分析所需的代码仓库、分支和版本；
4. 在代码中定位关键日志、字段、参数和失败分支；
5. 形成面向应用工程师的完整排查文档；
6. 从人版文档生成结构化的 Agent 执行版；
7. 明确缺失仓库和缺失日志造成的证据边界。

第一阶段优先专题：

1. 到点精度异常；
2. 导航运行参数异常；
3. 后续专题根据报表 Top 排名继续选择。

## 4. 两类知识系统

### 4.1 错误码排查文档

入口是明确的 JState 错误码，主要回答：

- 错误码由哪个模块、哪个条件触发；
- 对应日志和字段是什么；
- 应继续检查哪个上游模块；
- 错误如何恢复或清除。

### 4.2 高频问题排查文档

入口是现场现象，不要求一定存在错误码。一个高频问题可能跨越多个模块并关联多个错误码。

例如，到点精度异常可能涉及：

```text
任务目标点下发
→ 地图点位和属性
→ 路径终点生成
→ 定位数据
→ 运动控制与停车
→ 到点判定
→ 任务结果上报
```

两类文档相互引用：高频问题文档可以引用相关错误码文档，但不能用单个错误码替代完整的问题链路。

## 5. 输入材料

### 5.1 必要输入

- 问题统计报表；
- Top 问题的原始定义和典型现象；
- 相关模块的代码仓库；
- 与现场版本对应的分支、Tag 或提交；
- 代码中的日志语句、配置定义和接口结构。

### 5.2 可选验证材料

- TB 单正文、评论和最终结论；
- 现场日志；
- 配置、地图、截图和视频；
- 已知修复提交和复测记录。

这些材料用于验证和调整文档，但第一阶段不要求先把它们建设成完整 Case 数据集。

## 6. 标准工作流程

### 6.1 从报表确定 Top 问题

对报表进行统一归类，输出：

| 字段 | 说明 |
| --- | --- |
| 问题名称 | 稳定、可复用的问题名称 |
| 原始描述 | 报表中的提示或现象原文 |
| 频次 | 统计周期内出现次数 |
| 影响范围 | 项目、车型或车辆范围 |
| 当前分类 | 导航、定位、地图、参数或待确认 |
| 建设优先级 | 综合频次、影响和处理难度 |

标题只能用于问题归类，不能直接作为根因。

### 6.2 定义问题边界

每个专题开始前先明确：

- 什么现象属于该问题；
- 什么现象不属于该问题；
- 问题发生在哪个业务阶段；
- 有哪些可观察结果；
- 可能关联哪些错误码；
- 当前要覆盖哪些版本和车型。

### 6.3 建立仓库覆盖表

先画功能链路，再为链路中的每个节点找到代码仓库：

| 链路节点 | 负责模块 | 代码仓库 | 目标版本 | 是否已获得 | 分析状态 |
| --- | --- | --- | --- | --- | --- |
| 任务输入 | 待确认 | 待确认 | 待确认 | 否 | 阻塞于仓库缺失 |
| 地图与点位 | 待确认 | 待确认 | 待确认 | 否 | 待分析 |
| 导航规划 | 待确认 | 待确认 | 待确认 | 是/否 | 待分析 |
| 定位 | 待确认 | 待确认 | 待确认 | 是/否 | 待分析 |
| 运动控制 | 待确认 | 待确认 | 待确认 | 是/否 | 待分析 |
| 结果上报 | 待确认 | 待确认 | 待确认 | 是/否 | 待分析 |

缺少仓库时必须记录边界，不能用经验补写模块内部原因。

### 6.4 跨仓库代码审计

对每个链路节点查找：

1. 业务入口和接口；
2. 输入字段及其生产者；
3. 参数来源和默认值；
4. 状态机和关键条件；
5. 失败、降级、超时和恢复分支；
6. 日志语句、日志等级及打印字段；
7. 错误码和结果码；
8. 不同版本之间的相关变更。

每个结论应记录仓库、版本、文件和函数。行号只能作为辅助，因为版本变化后可能失效。

### 6.5 建立日志证据矩阵

日志排查必须从代码得出，而不是只写模糊关键词：

| 排查阶段 | 模块 | 日志特征 | 关键字段 | 正常判据 | 异常判据 | 对应代码分支 | 下一步 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 问题入口 |  |  |  |  |  |  |  |
| 上游输入 |  |  |  |  |  |  |  |
| 核心处理 |  |  |  |  |  |  |  |
| 结果判定 |  |  |  |  |  |  |  |
| 恢复验证 |  |  |  |  |  |  |  |

如果代码中没有打印完成判断所需的字段，应记录为“日志可观测性缺口”，而不是假设日志存在。

### 6.6 生成人版排查文档

人版文档建议结构：

1. 问题定义与适用范围；
2. 功能链路和涉及模块；
3. 仓库及版本覆盖情况；
4. 首轮日志时间窗和最小材料；
5. 日志字段提取表；
6. 逐级排查决策树；
7. 各分支的代码触发条件；
8. 支持证据、排除证据和停止规则；
9. 需要人工确认的处置建议；
10. 修复或调整后的验证方式；
11. 代码、版本和外部资料索引；
12. 未覆盖模块与可观测性缺口。

### 6.7 生成 Agent 执行版

Agent 版从人版派生，重点保留：

- 问题识别条件；
- 日志文件、时间窗和关键字；
- 需要提取的结构化字段；
- 字段比较和分支跳转；
- 结论置信度；
- 缺失证据；
- 下一步只读检查或人工交接；
- 复测验证条件。

Agent 不应根据代码可能性直接输出现场确定根因。

## 7. 到点精度异常的当前状态

现有 2412 文档已经完成 `nav-manager` 范围内的第一版代码审计：

- `source-docs/onsite-top/05-arrival-precision-2412.md`：人版；
- `source-docs/onsite-top/06-arrival-precision-2412-agent.md`：Agent 版。

它们目前应视为“单仓库范围内的第一版草稿”，还不能宣称覆盖到点精度异常的完整原因。

下一步需要先建立仓库覆盖表，确认到点精度链路实际涉及的任务输入、地图、导航、定位、控制和结果上报模块，再补齐各模块的日志字段和分支判据。

## 8. 导航运行参数异常的研究重点

该专题需要先从报表和代码确认：

- 报表中的“导航运行参数异常”具体指哪些参数；
- 参数由哪个模块定义、读取、校验和使用；
- 参数来自代码默认值、车型模板、配置文件、地图还是上游下发；
- 不同车型、导航模式和版本的合法范围；
- 异常值会在哪个模块、哪个分支留下什么日志；
- 参数变更和版本迁移是否可能改变默认值或语义。

在完成“参数—模块—车型—版本—场景”映射前，不输出通用推荐值，也不允许 Agent 自动修改参数。

## 9. 交付物

每个 Top 问题至少交付：

1. 问题定义和报表统计依据；
2. 跨模块功能链路图；
3. 仓库与版本覆盖表；
4. 日志证据矩阵；
5. 人版高频问题排查文档；
6. Agent 执行版文档或 Playbook；
7. 相关错误码索引；
8. 缺失仓库、缺失日志和未覆盖分支清单。

项目级交付：

1. Top 问题排序表；
2. 高频问题文档索引；
3. 错误码文档索引；
4. 文档生成和质量校验规则；
5. 持续更新的 `CHANGELOG.md`。

## 10. 验收标准

### 10.1 单篇文档验收

- 问题边界清晰，不把现象当根因；
- 功能链路中的每个节点都有负责模块；
- 已获得仓库的结论可追溯到版本、文件和函数；
- 每个主要分支都有对应日志或明确的可观测性缺口；
- 日志检查包含字段、正常判据和异常判据；
- 缺少仓库或现场证据时能够停止推断；
- 人版和 Agent 版的结论边界一致；
- 所有 Agent 操作符合只读边界。

### 10.2 整体建设验收

建议报告以下指标：

- Top 问题文档覆盖率；
- 功能链路仓库覆盖率；
- 已覆盖模块的日志字段覆盖率；
- 有确定性判断规则的分支比例；
- 被明确标记的仓库和可观测性缺口数量。

不以“枚举所有理论原因”或“仅凭代码自动确认现场根因”作为验收目标。

## 11. 当前边界

第一阶段暂不做：

- 建设完整 Case 数据集；
- 以 TB 单复核作为开始代码分析的前置条件；
- rosbag 自动分析；
- 自动 SSH 到机器人；
- 自动修改配置或参数；
- 自动重启服务；
- 自动控制车辆；
- 自动修改业务代码；
- 在仓库或证据不完整时补写确定性根因。

TB 单和历史现场材料可以作为文档验证样本，但不是当前知识建设的主数据模型。

## 12. 下一步执行顺序

1. 根据现有报表确认 Top 问题名称、频次和优先级；
2. 以“到点精度异常”为第一个专题，画出端到端功能链路；
3. 建立所需代码仓库和目标版本清单；
4. 标记已获得、缺失和版本不确定的仓库；
5. 在已有仓库中定位关键日志和字段；
6. 对缺失仓库提出明确的获取需求；
7. 仓库补齐后继续跨模块代码审计；
8. 重构 05 人版文档；
9. 从人版重新生成 06 Agent 版；
10. 使用已有现场日志或 TB 材料抽样验证排查路径。
