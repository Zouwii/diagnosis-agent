# 高频导航问题知识建设任务

## 1. 任务背景

应用工程师在处理 AGV 现场问题时，需要结合问题现象、TB 单、机器人日志、运行参数、代码和历史版本完成排查。当前知识材料以通用排查说明和源码机制说明为主，尚未形成由真实 Case 驱动、可追溯到版本和代码的高频问题知识体系。

2026 年 Q2 问题复盘显示：

- 共统计 196 个 TB 单；
- 导航类问题 142 单，占 72.45%，是占比最高的问题类型；
- 导航问题的原因不仅包含 `nav-manager` 等软件问题，还包括其他模块、外部因素和未知原因；
- “到点精度异常”是高频提示信息之一；
- “导航运行参数异常”已出现在出厂设置异常分类中；
- 很多问题没有明确报错，现场现象描述具有主观性；
- 现有排查文档存在覆盖不足、用户找不到对应文档、排查结论因人而异的问题。

因此，本任务不以“先做一个完整 Diagnosis-Agent”为目标，而是先建设两类高频问题的可验证知识底座，再决定哪些步骤适合规则化、检索或 Agent 编排。

## 2. 第一阶段目标

围绕以下两类高频导航问题，建立由真实 TB 单、代码和历史版本共同支撑的诊断指导文档：

1. 到点精度异常；
2. 导航运行参数异常。

第一阶段要回答的核心问题是：

> 当应用工程师遇到这两类现场问题时，系统能否根据现象和已有材料，给出覆盖主要已知 Case、证据可追溯、边界明确的排查指导？

第一阶段不是要实现自动根因诊断，也不承诺覆盖理论上的所有可能原因。“全覆盖”在本任务中定义为：覆盖选定时间范围内 TB 样本中已经出现且证据充分的原因类型，并明确尚未覆盖和证据不足的情况。

## 3. 目标用户与使用场景

### 3.1 目标用户

- 主要用户：负责现场问题排查的应用工程师；
- 次要用户：接收升级问题的导航研发、定位研发及相关模块研发；
- 知识维护者：能够读取 TB 单、代码仓库和版本记录的领域人员。

### 3.2 核心场景

应用工程师收到现场反馈后，需要：

1. 判断问题是否属于到点精度或导航运行参数异常；
2. 确认提单材料是否完整；
3. 根据现象和证据区分可能的问题分支；
4. 执行低风险检查和信息采集；
5. 给出临时处置、进一步取证或转研发建议；
6. 将最终结论回写为可复用 Case。

## 4. 当前材料审计结论

现有 `source-docs/onsite-top/` 文档具备源码调用链、日志关键词、可能原因和 Playbook 草稿，但暂时不能直接作为高质量诊断知识使用。

主要问题包括：

1. **Case 证据不足**：原因列表没有逐项关联具体 TB 单和最终处理结论；
2. **数据口径冲突**：Q2 原始材料、二次分类报告和现有文档中的到点精度异常数量不一致；
3. **从标题直接推断根因**：标题只能证明现场现象，不能证明最终原因；
4. **代码机制替代现场证据**：代码能说明某条链路如何工作，但不能单独证明某个 Case 的根因；
5. **版本边界不足**：虽然部分文档写了代码基线，但没有说明每个 TB Case 的现场版本及修复版本；
6. **原因互斥性不足**：定位、地图、调度、底盘、参数和导航软件等分支可能被同时罗列，缺少区分证据；
7. **验证标准偏理想化**：部分阈值和“连续 3 次”等判据尚未关联实际规范或 TB 处理记录；
8. **缺少参数专题**：导航运行参数异常还没有独立的问题定义、参数来源、版本默认值及校验方法。

在完成 TB Case 复核前，现有 onsite 文档只能视为待验证草稿，不能视为已经覆盖真实问题的正式结论。

## 5. 知识建设方法

### 5.1 先建立 TB Case 数据集

从 Q2 复盘和后续 TB 单中筛选与两类问题相关的 Case。每个 Case 至少记录：

| 字段 | 说明 |
| --- | --- |
| `case_id` | TB 单唯一标识与链接 |
| `problem_type` | 到点精度异常 / 导航运行参数异常 |
| `site` | 项目或现场 |
| `robot_id` | 机器人标识，敏感信息可脱敏 |
| `occurred_at` | 问题发生时间 |
| `symptom_raw` | 提单中的原始现象描述 |
| `error_or_prompt` | 错误码或提示信息；没有则明确记录“无” |
| `materials` | 日志、配置、地图、视频、截图等材料是否齐全 |
| `runtime_version` | nav-manager、nav-base、定位等相关版本 |
| `related_parameters` | 与 Case 有关的参数名、实际值和来源 |
| `final_cause` | 最终原因；未知则保留未知 |
| `cause_evidence` | 支撑最终原因的日志、配置、代码或复测证据 |
| `solution` | 实际采取的临时处置和根因修复 |
| `verification` | 修复后如何确认问题解决 |
| `owner_module` | 导航、定位、调度、底盘、部署或其他模块 |
| `confidence` | confirmed / likely / insufficient_data |

标题相似的重复 TB 单不直接计为不同原因；同一事件的重复提单需要建立关联。

### 5.2 再形成现象与原因分型

对每类问题分别完成：

1. 现场现象分型；
2. 最终原因分类；
3. 每种原因的支持证据与排除证据；
4. 适用版本和已知修复版本；
5. 缺少哪些材料时不能下结论；
6. 临时处置、根因修复与验证方法。

原因分类必须来自已复核的 TB Case。代码审计用于解释机制和补充检查点，不用于凭空扩展原因列表。

### 5.3 结合代码和历史版本验证

对每个已确认原因：

- 定位相关模块、配置项和调用链；
- 查找引入问题、修复问题或修改默认值的提交；
- 对比现场版本与修复版本；
- 确认日志关键词和参数是否在该版本真实存在；
- 记录可引用的文件、函数、提交或发布版本；
- 无法从代码或版本记录确认时，明确标记为待验证。

### 5.4 最后生成应用工程师指导文档

最终文档以“现场如何判断和行动”为主，而不是以源码模块为目录。建议结构：

1. 适用现象与不适用范围；
2. 首轮必须收集的材料；
3. 快速分流决策树；
4. 各原因分支的支持证据、排除证据和下一步；
5. 参数检查表或版本对照表；
6. 临时处置与风险提示；
7. 转研发条件与交接模板；
8. 修复验证；
9. TB Case、代码和版本证据索引；
10. 未覆盖 Case 和待补证据。

## 6. 两个专题的初始研究范围

### 6.1 到点精度异常

先从 TB 单确认以下分支是否真实存在及其频次，不预设它们都成立：

- 定位跳动、丢定位或定位精度不足；
- 二维码识别或二维码到点检查异常；
- 调度要求、点位或 footprint 等精度配置异常；
- 急停、复位、重新上道后的状态问题；
- 路径、目标点或伺服终点配置异常；
- nav-manager / nav-base 的历史版本缺陷；
- 外部模块或现场环境因素；
- 材料不足、最终原因未知。

### 6.2 导航运行参数异常

先从 TB 单确认：

- 哪些参数被实际判定为错误；
- 参数位于 ROS 参数、配置文件、地图、车型模板还是调度下发数据；
- 正常值来自代码默认值、车型基线、发布版本还是现场经验；
- 参数异常是出厂配置、部署修改、版本迁移、热更新或其他原因导致；
- 不同车型、导航模式和版本是否允许使用同一参考值；
- 修改参数的风险、权限、回退和验证方法。

在建立“参数—车型—版本—场景”关系前，不输出脱离上下文的推荐参数值，也不允许 Agent 自动修改现场参数。

## 7. 第一阶段交付物

1. 两类问题的 TB Case 清单；
2. Case 去重、材料完整性和最终原因复核结果；
3. 到点精度异常的原因树与证据矩阵；
4. 导航运行参数异常的参数清单与版本矩阵；
5. 两份面向应用工程师的诊断指导文档；
6. 一份未覆盖 Case 与证据缺口清单；
7. 可供后续 Diagnosis-Agent 使用的结构化规则或 Playbook 草稿。

## 8. 验收标准

第一阶段按知识质量验收，不按 Agent 功能数量验收：

- 纳入文档的每个已确认原因至少关联一个真实 TB Case；
- 每个 Case 保留原始现象、最终原因、处理方案和验证结果；
- 代码结论能够追溯到明确文件、函数、提交或版本；
- 文档能区分支持证据、排除证据和缺失证据；
- 不能确认的 Case 不强行归因，统一标记为 `insufficient_data`；
- 应用工程师能够根据文档完成首轮分流、材料采集和安全处置；
- 参数建议包含车型、版本、场景、风险和回退条件；
- TB 样本中新出现但未覆盖的分支能进入待补列表，而不是被错误归入已有原因。

“覆盖率”建议同时报告两个口径：

1. **Case 覆盖率**：指导文档可处理的已复核 Case 数 / 已复核 Case 总数；
2. **原因覆盖率**：已形成证据化指导的原因类型数 / TB 样本中已确认原因类型总数。

不使用“覆盖所有可能情况”作为不可验证的验收表述。

## 9. 暂不做

- 一开始覆盖全部导航、定位和建图问题；
- 仅凭代码枚举理论上的全部故障；
- 在没有 TB 结论的情况下自动生成根因；
- 自动 SSH、自动修改参数、自动重启或自动修复现场；
- 同时完成四种数据入口和完整多 Agent 编排；
- 把标题分类准确率等同于诊断准确率；
- 用 Q2 汇总数字代替 Case 级证据。

## 10. 后续执行顺序

1. 获取到点精度异常与导航运行参数异常的 TB 单及附件；
2. 建立 Case 表，完成去重和材料完整性检查；
3. 人工复核每个 Case 的最终原因和处理结果；
4. 按确认原因审计相关代码和历史版本；
5. 重写两份应用工程师指导文档；
6. 用历史 Case 回放文档，记录能解决、需追问和无法处理的 Case；
7. 根据回放结果决定哪些步骤进入确定性规则、检索知识或 Agent 工作流。

## 11. 下一步任务

下一步先处理“到点精度异常”：从 Q2 原始材料列出的相关 TB 单开始，读取单据正文、评论、附件、最终结论和版本信息，建立第一版 Case 表。完成 Case 复核前，不继续扩写现有 `04-arrival-precision.md` 的原因列表。
