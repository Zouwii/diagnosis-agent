# 架构说明

## 1. 产品定位

Diagnosis Agent 是 6001 端口上的 LangGraph 诊断工作流。它把已经验证过的诊断流程从
隐式 orchestrator 转换为具有明确 State、节点边界、Case 生命周期和安全契约的服务。

一期主题：**诊断流程结构化与可控化**。

## 2. 分层

```text
server/  API、认证、Case、Worker
   ↓
agent/   StateGraph、节点、checkpoint
   ↓
engine/  与 LangGraph 无关的采集、分析、报告能力
   ↓
source-docs/ + templates/  诊断知识与交付格式
```

依赖方向必须保持向下。Engine 不依赖 LangGraph，便于兼容基线与节点版本复用同一能力。

## 3. 版本

### origin-v1

```text
START → diagnosis_cli → END
```

单节点调用 `engine.workflows.run_case()`，覆盖采集、确定性分析、外部证据和报告。它用于
冻结原 orchestrator 的输入输出和 Case 文件，不承担后续功能演进。

### graph-v1

当前基线：

```text
START → collect → analyze → report → END
```

目标结构：

```text
collect → material_gate
  ├─ insufficient → human_interrupt
  └─ sufficient → signal_scan → diagnosis_route
                                  ├─ error_code_analysis
                                  └─ symptom_analysis
                                → evidence_reduce → report
```

graph-v1 的节点必须可以独立测试，节点间只通过 `DiagnosisState` 和稳定领域契约传递数据。

## 4. Case 与执行

API 创建 Case 后立即返回，Worker 从租户存储中领取 `pending` Case，并以 `case_id` 作为
LangGraph `thread_id`。Case 是业务事实来源，checkpoint 是图执行恢复来源，两者职责不同。

Case 至少保存：

- 租户与来源；
- 用户输入和采集参数；
- 当前状态和进度事件；
- 材料清单与安全路径；
- 诊断结论、缺失证据和报告路径；
- 运行版本及节点轨迹。

## 5. 安全边界

- 身份只接受 management-system Session 或内部签名 Header；
- Case、上传和报告均按 `owner_safe` 隔离；
- `local_logs` 只能读取当前租户 uploads 或 management-system 工作区；
- 采集与诊断默认只读；
- 报告路径必须位于当前 Case；
- mode 和运行版本使用固定白名单。

## 6. 知识层

`source-docs/jstate_error_codes/agent/` 提供错误码 Playbook；`source-docs/onsite-top/`
提供无错误码现场问题知识。`knowledge/playbook_loader.py` 是当前运行时加载入口。

知识生成工具和运行时知识必须区分：生成脚本负责维护资产，Graph 节点只读取已发布资产。

## 7. 非目标

- Claude CLI/ttyd 运行时；
- 多 Agent 自由协作、辩论或仲裁；
- 在 LangGraph 节点内复制一套新的诊断 Engine；
- 一期引入复杂基础设施或自动修改机器人状态。

5433 历史实现已隔离在 `legacy/ttyd-5433/`，不参与 6001 构建和运行。
