## 2. 服务层（server/）

### 2.1 FastAPI 入口（server/main.py）

- 端口：6001 起，脚本和启动检查拒绝小于 6001 的端口
- CORS：只允许 `DIAGNOSIS_CORS_ORIGINS` 中显式配置的来源
- 双身份源：
  - management-system Session Cookie → 回调 `${MANAGEMENT_SYSTEM_URL}/api/bt/auth/me`
  - 内部代理 Header（`X-Diagnosis-User-Id` + `X-Diagnosis-Internal-Token`）
- 不接受 body 中的 `ownerKey/user_id`
- 生产环境禁止匿名访问

### 2.2 Case API（server/api/cases.py）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/cases/uploads` | 上传租户日志材料，返回 `upload_id` |
| POST | `/api/cases` | 创建诊断 Case，写入持久化 case.json |
| GET | `/api/cases/{id}` | 查询 Case 状态，磁盘为权威来源 |
| GET | `/api/cases/{id}/stream` | SSE 进度推送，浏览器断开不中止诊断 |
| GET | `/api/cases/{id}/report` | 下载 Markdown 诊断报告 |

Case 创建流程：
1. 校验租户身份
2. 校验 mode 和必填参数（通过 `mode_registry.validate_mode_params`）
3. 写入 `case_dir/case.json`，状态 `pending`
4. 返回 Case Response，**不等待诊断完成**

SSE 设计：
- 只读取持久化 Case 记录的 `progress_events`
- API 和 Worker 是独立进程，SSE 不依赖内存状态

### 2.3 独立 Worker（server/worker.py）

- 不监听端口，通过文件队列实现持久性
- 轮询 `tenants/{owner}/cases/*/case.json`，处理 `pending` 状态
- 使用 `.worker.lock` 文件锁防止重复执行
- 通过 `server/case_runner.py` 调用 LangGraph 执行诊断

### 2.4 Case Runner（server/case_runner.py）

- 将 API Case 记录映射为 LangGraph 输入
- 异步执行编译后的 diagnosis graph
- 回写 Case 状态、报告路径和进度事件
- 最终状态：`closed`（confirmed/likely）或 `awaiting_human`

### 2.5 身份认证（server/auth.py + server/identity.py）

- 使用 `engine.tenant_storage.safe_owner_key` 计算 owner_hash
- 与 management-system 的 `runtime/users/{owner_safe}` 算法一致
- 所有 Case 查询和报告下载校验 `owner_safe`

## 3. 编排层（agent/）

### 3.1 LangGraph 图（agent/graph.py）

当前图结构为**单入口节点**：

```
START → run_cli_workflow → END
```

- `run_cli_workflow`（`agent/nodes/run_cli.py`）直接执行完整 CLI Engine
- 不包含来源识别、双 Agent 仲裁或多路 fan-out
- Checkpointer：优先 Postgres（`DATABASE_URL`），回退 MemorySaver

### 3.2 状态定义（agent/state.py）

`DiagnosisState` TypedDict 包含：
- 输入：`case_id`、`source_type`、`symptom`、`extra_params` 等
- 分析中间产物：`materials`、`findings`、`error_codes`、`problem_type`、`deep_insights`
- 结论：`conclusion_status`、`report_path`
- 控制：`errors`、`fallback_triggered`

### 3.3 采集节点（agent/nodes/collect.py）

- 四种来源的独立采集实现：`tb_task`、`internal_robot`、`remote_site`、`local_logs`
- 调用 `engine/collectors/dispatch.py` 的 `collect` 函数
- 本地日志路径校验：必须在租户 `uploads/` 或 management-system 工作区内

## 4. 引擎层（engine/）

从 `diagnosis-orchestrator` 迁移而来的模块化分析引擎，全部在项目内直接导入，不再通过子进程 CLI。

### 4.1 采集模块（engine/collectors/）

| 模块 | 文件 | 说明 |
|---|---|---|
| 调度 | `dispatch.py` | 统一入口，按 source_type 路由 |
| SSH 机器人 | `ssh_robot.py` | 内网机器人日志采集 |
| Teambition | `teambition.py` | TB 附件下载和解析 |
| 远程现场 | `remote_hand.py` | 远程现场材料采集 |
| 本地日志 | `local_logs.py` | 本地日志包处理 |

### 4.2 分析模块（engine/analysis/）

| 模块 | 文件 | 说明 |
|---|---|---|
| 问题分类 | `routing.py` | `classify_problem_type`，按 symptom 关键词匹配问题类型 |
| 日志扫描 | `material_scan.py` | 日志行分类、错误码提取 |
| 时间窗 | `timeline.py` + `windowing.py` | 时间戳解析、按时间窗截取日志 |
| 深层归因 | `deep_rules.py` + `deep_insights.py` | 6 项规则匹配，EMMA 错误解析 |
| 专项发现 | `insights.py` | 专项 skill 命中、历史 Case 召回 |
| 外部证据 | `external_evidence.py` + `external_providers.py` | 钉钉知识库、GitLab 代码检索 |
| 确定性分析 | `deterministic.py` | 主分析管道 |
| 证据选择 | `evidence_selection.py` | 证据关键词和优先级 |

### 4.3 报告模块（engine/reporting/）

- `formatters.py`、`renderers.py`、`reporter.py`：报告渲染和格式化

### 4.4 工作流模块（engine/workflows/）

- `run_case.py`：主 Case 执行流程（采集 → 分析 → 报告）
- `analyze_case.py`：分析流程
- `resume_case.py`：断点续跑
- `models.py`：流程数据模型

### 4.5 模式注册表（engine/mode_registry.py）

四种固定模式，服务端白名单映射：

| mode | 采集 Skill | 分析 Skill |
|---|---|---|
| `internal_robot` | `robot-peek` | `robot-diagnosis` |
| `tb_task` | `teambition` | `robot-diagnosis` |
| `remote_site` | `remote-hand` | `robot-diagnosis` |
| `local_logs` | `robot-diagnosis` | `robot-diagnosis` |

不接收客户端传任意 Skill 名称。

### 4.6 租户存储（engine/tenant_storage.py）

- 持久化目录布局：`{root}/tenants/{owner_safe}/cases/{case_id}/`
- Case record 以 `case.json` 的原子替换保证一致性
- 上传目录隔离：`{root}/tenants/{owner_safe}/uploads/`
- 支持 management-system 工作区作为可选的本地日志来源

## 5. 知识层（knowledge/）

### 5.1 Playbook 加载器（knowledge/playbook_loader.py）

- 从 `source-docs/jstate_error_codes/agent/` 加载 54 个 Agent 错误码文档
- 提取 YAML playbook 段，执行确定性检查（grep 日志 → 触发链匹配）
- 支持列出所有可用错误码、加载轻量 meta 信息

### 5.2 TopK 文档加载器（knowledge/topk_loader.py）

- 加载 B 类文档（现场问题排查文档），按错误码或问题类型做关键词匹配
- 错误码 → 分类映射（共 50 个错误码，8 个分类）
- 问题类型 → 排查方向关键词

## 9. 与历史设计的差异

当前实现与早期 12 节点、多 Agent 架构方案的主要差异（历史方案已归档到 `docs/archive/`）：

| 方面 | 历史设计 | 当前实现 |
|---|---|---|
| LangGraph 节点 | 12 个独立节点（identify, classify, doc_agent 等） | 1 个节点（run_cli_workflow） |
| Agent 数量 | 3 个（doc_agent + field_agent + arbitrate） | 0（分析逻辑在 engine 中） |
| CLI 集成 | 子进程调用 jz-claude-skills | 引擎全量迁移到 engine/ 直接 import |
| 知识加载 | 引外部 nav-manager 仓库 | 知识副本在 source-docs/，loader 加载本地 agent/ |
| 模式路由 | LLM 猜测来源 | 服务端固定 mode→Skill 白名单 |
| 部署 | API + CLI 子进程 | API + 独立 Worker（文件队列，持久化） |
