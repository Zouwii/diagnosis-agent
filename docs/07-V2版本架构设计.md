# Diagnosis-Agent V2 版本架构设计

> 日期：2026-08-11  
> 状态：待开发  
> 核心策略：优先恢复可用的 Claude + Skill 路线，LangGraph 只做最小验证；V1 代码暂不删除、暂不重构。

## 1. 背景与决策

原有 ttyd 路线的核心能力并不来自 ttyd，而是来自 Claude Code 对
`diagnosis-orchestrator` 和一组专项 Skills 的自主调用。ttyd 只是把终端交互暴露给浏览器。

当前 Diagnosis-Agent 已具备 6001 Web/API、Case 存储、文件队列 Worker、SSE 和一套迁移后的
Python Engine，但当前 `origin-v1` 只执行确定性 `diagnosis_cli`，没有复刻 Claude 在 Skill
约束下继续读取材料、选择工具、深层推理和追问用户的行为。

V2 不继续扩大 LangGraph 开发范围，而采用双运行时：

1. **Claude 稳定模式**：直接运行完整 `diagnosis-orchestrator`，作为 6001 默认生产路线。
2. **LangGraph 实验模式**：只使用一个诊断节点，节点内部复用同一个 Claude Runner，用于验证状态管理、可观测性和 Token 成本。
3. **V1 Legacy 模式**：保留现有 `origin-v1`、`origin-split` 和 Python Engine，暂不删除，也不作为 V2 新功能的主要开发位置。

## 2. V2 目标与非目标

### 2.1 目标

- 用户通过 6001 页面提交四类诊断来源，并获得旧 Claude 路线相近的诊断行为。
- 浏览器通过 SSE 查看持续进度，断开浏览器不影响后台任务。
- 完整 Skills 随 Diagnosis-Agent 版本发布，服务器不依赖外部漂移目录。
- 每个 Case 记录模型、Token、估算成本、耗时、工具调用和最终状态。
- 支持诊断过程暂停为 `awaiting_human`，用户补充信息后续接同一 Claude Session。
- LangGraph 一期保持最小复杂度，并和稳定模式复用同一执行能力。

### 2.2 非目标

V2 一期明确不做：

- 多 Agent 自由协作、辩论或仲裁；
- 将 orchestrator 拆成大量 LangGraph 节点；
- 自研模型路由平台；
- 自动修改机器人配置、重启服务或执行发版；
- 一期引入 PostgreSQL、消息队列、Kubernetes 等基础设施；
- 在 V2 验收前删除或重写现有 V1 Engine。

## 3. 总体架构

```text
Browser / Management-System
            │
            ▼
┌─────────────────────────────────────────────┐
│ Diagnosis API :6001                         │
│ - 创建/查询 Case                            │
│ - 上传材料                                  │
│ - SSE 事件流                                │
│ - 人工补充信息                              │
│ - 报告与运行指标                            │
└──────────────────────┬──────────────────────┘
                       │ 持久化 case.json
                       ▼
┌─────────────────────────────────────────────┐
│ File Queue Worker                           │
│ - claim Case                                │
│ - Runtime Router                            │
│ - 超时/并发/预算控制                         │
└───────────────┬─────────────────┬───────────┘
                │                 │
                ▼                 ▼
┌───────────────────────┐  ┌────────────────────────┐
│ Claude 稳定模式        │  │ LangGraph 实验模式      │
│ ClaudeOriginRunner    │  │ START                  │
│                       │  │   ↓                    │
│ /diagnosis-           │  │ claude_diagnosis      │
│ orchestrator          │  │   ↓                    │
│ + bundled skills      │  │ END                    │
└───────────┬───────────┘  └────────────┬───────────┘
            │                           │
            └───────────┬───────────────┘
                        ▼
             同一 ClaudeOriginRunner
                        │
                        ▼
┌─────────────────────────────────────────────┐
│ Shared Case Substrate                       │
│ raw / extracted / events.jsonl / report.md  │
│ session.json / usage.json / case.json       │
└─────────────────────────────────────────────┘
```

核心原则是：**两个模式只改变编排入口，不复制诊断能力。**

## 4. 版本与产品展示

### 4.1 内部运行时名称

| runtime | 实现 | 定位 |
|---|---|---|
| `claude-origin-v1` | Worker 直接调用 `ClaudeOriginRunner` | V2 默认稳定路线 |
| `graph-v1` | 单节点 LangGraph 调用 `ClaudeOriginRunner` | 实验与指标比较 |
| `engine-cli-v1` | 当前确定性 `diagnosis_cli` | Legacy 兼容路线 |
| `engine-split-v1` | 当前 collect/analyze/report 图 | Legacy 研究路线 |

现有 API 中的 `origin-v1`、`origin-split` 暂时保留。V2 开发时通过兼容映射逐步引入新名称，
避免直接破坏已有 Case 和测试。

### 4.2 6001 页面展示

普通用户只看到：

- **稳定模式（默认）**：Claude + 完整诊断 Skills；
- **实验模式**：LangGraph 单节点流程。

Legacy 名称只在开发配置或调试页面中出现。

## 5. 核心模块

### 5.1 Runtime Router

Worker 根据 Case 的 `runtime` 选择执行器：

```python
RUNNERS = {
    "claude-origin-v1": ClaudeOriginRunner,
    "graph-v1": LangGraphRunner,
    "engine-cli-v1": LegacyEngineRunner,
}
```

Router 只做白名单选择，不允许客户端传入任意 Python 类名、命令或 Skill 路径。

### 5.2 ClaudeOriginRunner

职责：

1. 为 Case 创建独立工作区；
2. 写入 V2 `CLAUDE.md` 环境约束；
3. 将发布包中的 Skills 链接到 Case 私有 Claude 配置目录；
4. 构造固定入口 Prompt，强制首先调用 `diagnosis-orchestrator`；
5. 以非交互流式模式启动 Claude CLI；
6. 解析标准输出中的 JSON 事件并持久化；
7. 保存 Session ID、Token、耗时、模型和退出状态；
8. 检查 `report.md` 和材料门禁，生成最终 Case 状态；
9. 需要补充信息时进入 `awaiting_human`，收到回答后恢复 Session。

建议命令形态：

```bash
claude \
  -p "<固定诊断入口 Prompt>" \
  --output-format stream-json \
  --include-partial-messages \
  --add-dir "<bundled_skills_root>" \
  --session-id "<session_id>" \
  --max-budget-usd "<case_budget>"
```

具体参数以服务器已安装 Claude CLI 版本为准。Runner 必须使用参数数组启动子进程，不能拼接
用户输入后交给 shell 执行。

### 5.3 LangGraphRunner

一期图结构：

```text
START → claude_diagnosis → END
```

`claude_diagnosis` 只负责：

- 将 LangGraph State 转换为统一 RunnerRequest；
- 调用 `ClaudeOriginRunner`；
- 将 RunnerResult 回写 State；
- 记录节点级 Token、耗时和结果。

一期不在 LangGraph 内重新实现 Skill 路由、采集和报告逻辑。未来只有在真实数据证明某一步
成本高、失败率高或需要人工审批时，才拆出独立节点。

### 5.4 Skills Bundle

V2 发布包包含一份固定版本的 `jz-claude-skills`：

```text
diagnosis-agent/
└── bundled_skills/
    ├── skills/
    │   ├── diagnosis-orchestrator/
    │   ├── teambition/
    │   ├── robot-peek/
    │   ├── remote-hand/
    │   ├── robot-diagnosis/
    │   └── ...
    ├── scripts/
    └── VERSION
```

一期为了降低依赖遗漏风险，直接迁移完整 `skills/` 和公共 `scripts/`。`VERSION` 至少记录来源
仓库 commit。发布后不再依赖 `/home/jz/diagkit/jz-claude-skills` 的当前内容。

构建时复制，源码仍以 `jz-claude-skills` 仓库为准，避免人工维护两套 Skill。

### 5.5 Case 与事件存储

延续当前文件存储，不引入数据库：

```text
${DIAGNOSIS_STORAGE_ROOT}/tenants/{owner_safe}/cases/{case_id}/
├── case.json
├── request.json
├── workspace/
│   ├── CLAUDE.md
│   └── .claude/skills/
├── raw/
├── extracted/
├── events.jsonl
├── session.json
├── usage.json
├── claude-result.json
├── report.md
└── human-handoff.md
```

`events.jsonl` 是 SSE 的事实来源。浏览器断开不会终止 Worker，重新连接时通过事件序号恢复。

## 6. 关键流程

### 6.1 创建并执行 Case

```text
POST /api/cases
  → 校验四类来源参数
  → 写入 pending Case
  → Worker claim
  → status=running
  → Runner 创建隔离工作区
  → Claude 调用 orchestrator 和专项 Skills
  → 持续写 events.jsonl
  → 生成并校验 report.md
  → closed / awaiting_human / failed
```

### 6.2 人工补充与续跑

新增接口：

```text
POST /api/cases/{case_id}/messages
```

请求只接受用户文本和可选附件 ID。服务端读取 `session.json`，通过 Claude CLI 的 Session
恢复能力继续执行。人工回答不得直接拼入 shell 命令。

### 6.3 SSE 重连

```text
GET /api/cases/{case_id}/stream
Last-Event-ID: 42
```

服务端从第 43 条事件开始发送。SSE 断开只影响展示，不影响诊断进程。

### 6.4 材料门禁

进入深层诊断前必须检查采集结果：

- TB 403、任务不存在或活动/附件未取得时，标记 `collection_failed` 或
  `insufficient_data`；
- 本地路径不存在、SSH 失败、远程隧道失败时，不得生成看似完整的通用根因；
- 只有材料满足最低条件时才进入分析；
- 报告必须区分“诊断结论”和“采集失败说明”。

## 7. API 与状态契约

### 7.1 创建 Case

```json
{
  "mode": "tb_task",
  "runtime": "claude-origin-v1",
  "task_url": "https://...",
  "symptom": "小车执行任务时异常停止",
  "time_window": "2026-08-11 10:00"
}
```

`runtime` 可省略，默认读取 `DIAGNOSIS_DEFAULT_RUNTIME`。

### 7.2 Case 状态

```text
pending
  → preparing
  → running
      ├─ awaiting_human → pending/resuming → running
      ├─ closed
      └─ failed
```

采集失败可以使用业务结果 `insufficient_data`，但执行状态仍结束为 `closed`；只有进程异常、
超时且无可交付结果、存储错误等技术故障才标记 `failed`。

### 7.3 产品事件

V2 将 Claude 原始事件转换成稳定的产品事件：

```text
case.created
execution.started
skill.started
skill.completed
tool.started
tool.completed
material.collected
collection.failed
human.required
usage.updated
report.generated
execution.completed
execution.failed
```

前端依赖产品事件，不直接依赖某一版 Claude CLI 的原始 JSON 字段。

## 8. Token、成本与产品指标

每个 Case 至少记录：

```json
{
  "runtime": "claude-origin-v1",
  "model": "deepseek-v4-flash",
  "input_tokens": 12840,
  "output_tokens": 3520,
  "total_tokens": 16360,
  "estimated_cost_usd": 0.018,
  "duration_ms": 96231,
  "tool_calls": 14,
  "skills": ["diagnosis-orchestrator", "teambition"],
  "result": "insufficient_data"
}
```

一期产品看板只需要五个核心指标：

1. 单 Case 平均 Token 与 P90；
2. 单 Case 平均估算成本；
3. 从提交到报告的平均耗时；
4. `confirmed/likely/need_human/insufficient_data` 分布；
5. 人工介入率。

实验模式额外记录 LangGraph 节点 Token 和耗时，用来判断以后是否值得拆图，而不是预设复杂架构。

## 10. 安全边界

- 每个租户、每个 Case 使用独立工作区和 Claude 配置目录；
- 不再删除或覆盖全局 `~/.claude/skills`；
- 默认只读诊断，禁止重启、改配置、发版和机器人写操作；
- 使用工具白名单、超时、预算、并发上限和输出大小限制；
- 用户输入只作为 Prompt 数据，不参与命令拼接；
- 事件和报告输出前屏蔽 API Key、Token、Cookie 和密码；
- 高风险动作必须进入 `awaiting_human`，V2 一期不实现自动执行；
- 保留原始 Claude 输出供审计，但普通前端只展示稳定产品事件。

## 11. ttyd 的位置

V2 不依赖 ttyd 才能工作。6001 + Worker + SSE 是普通用户主入口。

ttyd 暂时保留为：

- 专家调试；
- 诊断失败后的人工接管；
- V2 与旧 Claude 行为比较；
- V2 上线初期的回退入口。

V2 稳定后再决定是否下线 ttyd，当前阶段不删除相关脚本。

## 12. Legacy 隔离原则

V2 开发期间以下内容原则上只修阻断性 Bug，不继续扩建：

- 现有 `engine/` 确定性诊断流程；
- 现有 `origin-v1`、`origin-split` 语义；
- 旧多 Agent、模型路由和复杂 Harness 设想；
- ttyd 登录代理和终端脚本。

新增代码优先放入：

```text
runners/
├── base.py
├── claude_origin.py
├── langgraph_runner.py
└── legacy_engine.py

runtime/
├── events.py
├── usage.py
├── workspace.py
└── policy.py

prompts/
└── CLAUDE.md
```

避免继续把 V2 逻辑堆进 `agent/nodes/` 或 `engine/`。

## 13. 开发阶段

### Phase 0：冻结基线

- 保留当前 V1 测试和服务器版本；
- 选择 3 至 5 个历史 Case 作为回归样本；
- 固定旧 ttyd 路线输出，作为行为比较基线。

### Phase 1：6001 Claude 稳定模式

- 将完整 Skills 纳入部署包；
- 实现 Case 私有工作区；
- 实现 `ClaudeOriginRunner`；
- 将 stream-json 转成持久化产品事件和 SSE；
- 获取报告、Session 和 Token 数据；
- 将 6001 默认模式切到 `claude-origin-v1`。

### Phase 2：人工续跑与可靠性

- 增加 messages 接口和 Session 恢复；
- 支持 SSE 事件序号与断线重连；
- 增加超时、预算、并发和敏感信息过滤；
- 完成采集失败门禁。

### Phase 3：极简 LangGraph

- 增加单节点 `graph-v1`；
- 复用同一个 Claude Runner；
- 记录节点级耗时和 Token；
- 对比稳定模式和实验模式结果，不影响默认用户路径。

## 14. 验收标准

### 14.1 功能验收

- 四类来源都能从 6001 创建 Case；
- 默认路线实际调用 `diagnosis-orchestrator`，而不是只执行确定性 Python CLI；
- SSE 断开后 Worker 继续执行，重连可以恢复事件；
- 报告、原始材料、Session 和 Usage 都归档到正确租户；
- Claude 要求补充信息时可以暂停和续跑；
- TB 403 等采集失败不会生成虚假的通用根因。

### 14.2 一致性验收

对相同冻结材料分别运行旧 ttyd 路线和 `claude-origin-v1`，比较：

- 是否调用 orchestrator；
- 关键 Skills 和工具调用是否一致；
- 证据覆盖是否一致；
- 结论状态和根因方向是否一致；
- 缺失材料与人工追问是否一致。

不要求逐字相同。首期目标是关键行为一致，且 V2 不比旧路线更容易在证据不足时猜测根因。

### 14.3 成本验收

- 每个 Case 都能输出 Token、耗时和估算成本；
- 可按 runtime 聚合稳定模式与实验模式；
- 单 Case 超过预算时有明确终止事件和可交付说明；
- 指标缺失不能阻断报告，但必须记录原因。

## 15. 后续演进触发条件

只有满足以下任一条件，才考虑把 LangGraph 拆成多节点：

- 某类采集重复消耗大量 Token；
- 某一步失败率显著高，需要独立重试；
- 某一步必须经过人工审批；
- 不同问题类型需要明显不同的模型或预算；
- 单节点上下文过长，拆分后有可量化成本收益；
- 需要对某个阶段做独立评测和版本控制。

在没有运行数据前，不为面试展示预先建设复杂多 Agent 系统。

## 16. V2 一句话定义

> Diagnosis-Agent V2 是一个把成熟 Claude Skills 产品化的诊断服务：通过 6001 提供统一 Case、SSE、报告、人工续跑和成本观测，并用极简 LangGraph 验证工作流可控性，为后续是否拆分 Agent 提供数据依据。
