## Skill: diagnosis-orchestrator

# 技术支持诊断编排入口

本 skill 是技术支持问题诊断的短期统一入口。它不重复实现专项诊断知识，只负责识别输入来源、建立 case 上下文、调用现有 skills、统一产出格式。

## 使用边界

- 默认只读诊断，不执行机器人写操作、重启服务、修改配置或发版。
- 不绕过 Teambition、钉钉、GitLab 的当前用户权限。
- 不上传日志、钉钉知识库文档、Teambition 任务内容到第三方系统。
- `dingtalk-writer` 仅在用户确认后用于发布或更新钉钉知识库文档。

## 快速流程

1. 识别输入来源：TB 任务、远程现场、公司内网机器人、本地日志包或信息不足。
2. 建立 case 上下文，至少记录 `case_id`、`source_type`、`symptom`、`time_window`、`knowledge_sources`、`code_sources`。
3. 调用数据采集 skill：
   - 公司内网机器人：`robot-peek`
   - 客户现场远程：`remote-hand`
   - Teambition 任务：`teambition`
   - 本地日志包：直接交给 `robot-diagnosis` 离线分析
4. 调用 `robot-diagnosis` 做基础诊断和时间线分析。
5. 根据证据分流到专项 skill：
   - 任务链路：`task-engine-troubleshoot`
   - 传感器/激光/相机：`device-log-analyzer`
   - 机型配置：`robot-model-config`
6. 需要已有经验、SOP、错误码解释或排查指南时，调用 `dingtalk-docs`，最多读取 5 篇正文。
7. 需要代码、MR、Issue、提交或流水线证据时，调用 `gitlab-operator`。
8. 输出诊断报告；如果不能闭环，同时输出人工介入清单。
9. 钉钉知识库没有覆盖或已有文档不完整时，输出钉钉知识库沉淀草稿。

## 输入识别

按优先级判断：

| 输入特征 | 来源类型 | 首选数据源 |
|---|---|---|
| 包含 TB 链接或 taskId | `tb_task` | `teambition` |
| 包含 frp 端口、远程之手、客户现场实时排查 | `remote_site` | `remote-hand` |
| 包含 172.x IP | `internal_robot` | `robot-peek` |
| 包含本地日志包路径 | `local_logs` | `robot-diagnosis` |
| 只有现象描述 | `insufficient_data` | 追问最小信息 |

如果信息不足，只问一个阻塞问题，例如：“这是公司内网机器人、TB 任务、远程现场，还是本地日志包？”

## Case 上下文

每次诊断都维护以下上下文：

```yaml
case_id:
source_type: internal_robot | tb_task | remote_site | local_logs
symptom:
time_window:
robot_identity:
artifacts:
knowledge_sources:
code_sources:
analysis_route:
conclusion_status: confirmed | likely | need_human | insufficient_data
```

## 结论可信度

| 状态 | 使用条件 |
|---|---|
| `confirmed` | 日志、状态、代码或钉钉知识库证据闭环，能解释现象 |
| `likely` | 证据强相关，但缺少最终验证 |
| `need_human` | 需要现场操作、复现、硬件检查或补充权限 |
| `insufficient_data` | 缺少关键日志、时间点、任务信息或访问条件 |

## 输出模板

使用本 skill 的模板文件：

- 诊断报告：`templates/diagnosis-report.md`
- 人工介入清单：`templates/human-handoff.md`
- 钉钉知识库沉淀草稿：`templates/knowledge-draft.md`

详细路由规则见 `references/routing-rules.md`。

## 命令行入口

中期命令行入口已提供：

```bash
./scripts/diagnosis
```

无参数运行时会读取当前目录下的 `diagnosis.config.json`。如果文件不存在，脚本会自动生成模板；编辑后再次运行即可创建 case。

`./scripts/diagnosis` 会按来源先分桶，再在来源目录下创建 case：

- `tb_task` → `diagnosis-cases/teambition/<case_id>/`
- `internal_robot` → `diagnosis-cases/robot-peek/<case_id>/`
- `remote_site` → `diagnosis-cases/remote-hand/<case_id>/`
- `local_logs` → `diagnosis-cases/local/<case_id>/`

每个 case 目录内部再放 `raw/`、`extracted/`、`tmp/`、`report.md` 等内容。其中 `tb_task` 会自动拉取任务详情、评论和附件，并同步到当前 case 的 `raw/` 与 `extracted/`；附件默认会先按 5GB 阈值自动筛选，超过阈值的文件会被记录为待确认项；**默认跳过对诊断无价值的二进制文件（.bag / .mp4 / .png 等），加 `--allow-all-attachments` 可强制下载全部附件**。`local_logs` 会把你给的本地日志路径直接导入到当前 case 的 `raw/`。需要强制下载大文件时可加 `--allow-large-downloads`。

创建或 resume 后，CLI 会默认执行一轮材料采集、本地分析和只读外部证据补充：`internal_robot` 会通过 `sshpass + ssh` 对目标机器人执行只读巡检命令，把版本、状态、错误、ROS、进程和关键日志摘录保存到 `raw/robot/`；`remote_site` 会通过远程之手 frp 端口连接 Windows 工具包，再用 `ssh-robot.py` 对现场机器人执行同一套只读巡检命令，并保存到 `raw/remote-hand/`；然后扫描 `raw/` 和 `extracted/` 下的可读文本日志、JSON、YAML、Markdown，提取错误码、ERROR/WARN/异常关键词，推断后续专项 skill 路由，并把任务链路、设备日志、机型配置三类专项命中证据写入报告

## Skill: robot-diagnosis

# 机器人系统诊断

迦智机器人本体系统的系统性分析与问题排查入口。支持**在线分析**（实时诊断当前状态）和**离线分析**（从日志反推历史问题）两种模式。

**核心设计：症状路由优先。** 大部分问题不需要走完整巡检流程——根据症状直接跳到对应的深度排查路径即可。系统巡检（操作系统→迦智状态→异常分析）仅在"车有问题但不清楚具体是什么"时作为兜底。

---

## 诊断技能全景与协作

诊断相关技能分两层：**传输层**负责"怎么连上去"，**分析层**负责"诊断什么"。

```
分析层（"诊断什么"）
  ├─ robot-diagnosis          ← 本技能：系统总入口，症状路由 + 兜底巡检
  ├─ task-engine-troubleshoot ← 专项：任务链路（web-service / async-service / 行为树）
  ├─ device-log-analyzer      ← 专项：传感器日志（jrosth / jzhw / 激光雷达 / 相机）
  ├─ scan-filter-diagnosis    ← 专项：感知（scan_filter 配置/滤波/数据质量/盲区）
  └─ robot-model-config       ← 专项：机型配置（设置/检查）+ 机型类问题反向诊断
  └─ embedded-troubleshoot    ← 专项：嵌入式硬件（电机/驱动/IO/举升/总线/停障/电源等）

传输层（"怎么连上去"）
  ├─ robot-peek    ← 内网 172.x.x.x 直连
  └─ remote-hand   ← 客户现场 frp 隧道
```

**典型调用栈**：用户描述问题 → 按症状路由到深度排查路径 → 必要时调用传输层建立连接 → 必要时跳转到专项分析层。

## 技术支持诊断入口交接

当请求来自 `diagnosis-orchestrator`，或用户输入同时包含机器人 IP、TB 任务、远程现场端口、本地日志包、钉钉知识库范围、GitLab 仓库/MR/Issue 等上下文时，本技能作为分析层执行，不重新发明入口流程。

交接规则：

1. 接收并保留 case 上下文：`case_id`、`source_type`、`symptom`、`time_window`、`robot_identity`、`artifacts`、`knowledge_sources`、`code_sources`。
2. 先建立诊断时间线，再按症状路由到专项 skill。
3. 需要已有排查经验、错误码解释、历史 SOP 或模块设计背景时，调用 `dingtalk-docs`，最多读取 3 篇正文。
4. 需要代码实现、历史修复、MR、Issue 或流水线证据时，调用 `gitlab-operator`。
5. 输出必须标注结论状态：`confirmed` / `likely` / `need_human` / `insufficient_data`。
6. 钉钉知识库没有覆盖或已有文档不完整时，生成钉钉知识库沉淀草稿，发布动作交给 `dingtalk-writer` 且必须人工确认。

推荐输出使用 `diagnosis-orchestrator/templates/diagnosis-report.md` 的结构。

## 安全规则（不可跳过）

### 密码编码存储

机器人 SSH 密码已 base64 编码存储，避免明文出现在终端日志中。使用时解码：

```bash
echo 'cm9ib3QxMjM=' | base64 -d
# 产出: robot123
```

在 Bash 命令中，用 `"$(echo 'cm9ib3QxMjM=' | base64 -d)"` 代替明文密码。

| 网段 | 策略 | 说明 |
|------|------|------|

| `172.18.*` | 优先 | 开发/测试机器人 |

> **⚠️ 172.23 网段为生产环境，操作不当可能影响线上业务。连接前必须再次向用户确认。只读原则仍然适用。**

`172.23.*` 的机器人正常出现在列表中，但展示时必须附加醒目的生产环境警告标识。连接前需二次确认用户意图。

## Skill: remote-hand

# 迦智远程之手

通过公网服务器 frp 反向隧道 + Windows 中转笔记本，远程接入客户现场——诊断局域网内的机器人、分析已采集的日志和资料、或执行远程工作。

---

## 安全规则（不可跳过）

### 继承 robot-peek 规则

连接到机器人后，**完全遵守 robot-peek 技能的安全规则**：
- 只读原则：命令白名单/黑名单
- 172.23.* 生产网段默认禁止访问
- 写操作拦截机制

### 额外安全规则

| 规则 | 说明 |
|------|------|
| Windows 端只写 workspace | 仅 workspace/ 目录内允许写操作，其他位置只读 |
| 文件传输 | 允许通过透传模式的 scp/sftp 双向传文件（见「文件传输与 SOCKS5 代理」）；小文件（≤ 2MB）仍可用 base64 经 SSH stdout 直接查看 |
| 连接信息不留存 | 不将服务器 IP、端口、凭证写入日志或缓存 |
| 会话结束提醒 | 诊断完成后提醒现场人员关闭 start.bat |

### 连接密码（版本兼容）

工具包有两套密码机制：

| toolkit 版本 | 密码 | 说明 |
|---|---|---|
| **v1 / v2 / v3** | `robot123` | 固定默认密码 |
| **v4+** | 随机生成 | 8 位（大小写字母 + 数字），启动时在控制台显示 |

**AI 连接策略：先试旧密码，失败再索要：**

```bash
# 先尝试 v1-v3 默认密码
export TUNNEL_PASS="$(echo 'cm9ib3QxMjM=' | base64 -d)"
```

连接验证（见 Step 1）。若认证失败（`Permission denied`），说明现场是 v4+ toolkit，向用户索取控制台显示的随机密码后更新：

```bash
export TUNNEL_PASS='<现场人员提供的8位随机密码>'
```

后续所有 `sshpass` 命令统一使用 `"$TUNNEL_PASS"` 引用密码。透传模式（ProxyCommand）中，`$TUNNEL_PASS` 需已 `export`，因为 ProxyCommand 由 ssh 在子 shell 中执行，需要从环境变量继承。

## 网络拓扑

```
AI (Claude Code)
    │
    │ SSH (公网服务器:映射端口, user=jz, password=随机)
    ▼
公网服务器 (frps)
    │
    │ frp 反向隧道 → 端口 2222
    ▼
Windows 笔记本 (Python SSH 服务器 + frpc)
    │
    │ paramiko SSH (局域网 robot IP:22)
    ▼
机器人 (jz@192.168.x.x)
```

Windows 端运行内置的 Python SSH 服务器（sshd.py），不依赖 Windows OpenSSH。SSH 服务器：
- 用户名：`jz`，密码：v1-v3 为固定 `robot123`，v4+ 为每次启动随机生成，见「连接密码」
- 工作目录（CWD）为 `workspace/`

## 前置条件

1. **公网服务器**：frps 已运行
2. **客户现场 Windows 笔记本**：已解压工具包并运行 `start.bat`
3. **用户已提供**：frp 映射端口号

> ⚠️ **同一台 Windows 上只能开一个 toolkit（v2 和 v3 不能并存）。** toolkit 硬编码 `LISTEN_PORT=2222`（sshd.py）和 frp `admin_port=7400`，两套工具包目录里这两个值完全相同。同时开两个 `start.bat` 会出现：第二个 frpc 报 `admin server error: listen tcp 127.0.0.1:7400: bind ... only one usage ... permitted`（7400 被占），两个 sshd.py 抢 2222——**先启动的旧进程继续服务 2222，后开的根本没接管**。结果：frp 给了新端口、窗口也打印新 VERSION，但隧道背后挂的还是**旧 sshd.py**，VERSION / 透传能力仍停在旧版本。升级 toolkit 时务必先**关掉旧的**（任务管理器结束所有 toolkit 目录下的 `python.exe` 和 `frpc.exe`，或直接关掉旧 `start.bat` 窗口）再开新的。

## Skill: teambition

# Teambition 任务查阅与管理

帮助开发者通过 Claude Code 查阅和管理 Teambition 项目、任务、任务详情、评论和附件。支持读取和写入操作。使用 Teambition Open API（经钉钉代理转发）作为主要数据源，钉钉项目 API 作为补充。

---

## 安全规则（不可跳过）

### 操作权限

**允许：**
- 读取项目、任务、评论、附件信息
- 更新任务字段（标题、描述、执行人、截止日期、优先级、状态、自定义字段）
- 发布评论（自动添加 `🤖 [AI评论]` 前缀）

**禁止：**
- 删除任务、删除评论、删除附件
- 任何不可逆的删除操作

### 评论标识

所有通过 AI 发布的评论，内容开头必须添加 `🤖 [AI评论]` 前缀，以标识来源。

### 主动操作限制（不可跳过）

**以下操作必须有用户明确要求才能执行，严禁 AI 主动发起：**

- ❌ **禁止主动修改任务状态**（isDone、stageId）—— 用户没说"关闭任务"/"标记完成"/"改状态"，就不能动
- ❌ **禁止主动发布评论** —— 用户没说"加条评论"/"回复一下"/"帮我评论"，就不能发
- ❌ **禁止主动修改任何任务字段** —— 包括标题、描述、执行人、截止日期、优先级、自定义字段等

即使分析完成后认为"应该同步到评论区"，也不能主动发布。只能在用户明确说"把分析结果发到单子上"之类的话时才执行。

**唯一例外**：用户问题中已隐含写入意图时可视作明确要求。例如：
- "帮我分析下这个问题" → 只读，不评论、不改状态
- "帮我分析下这个问题，结果发到评论区" → 可以评论
- "分析完帮我关闭这个单子" → 可以改状态

### 身份（写操作）

写操作（评论、更新任务）的 `X-Operator-Id` 由**代理按当前认证身份注入**（proxyToken/robot → unionId → Teambition userId）。技能**不得也不需要**在请求中传 `X-Operator-Id`——代理会忽略并覆盖任何传入值。

### 凭据安全

- 技能**不持有任何密钥**（AppId/SecretKey），所有 Teambition 请求经钉钉代理，凭证由代理服务端托管。
- 不将 token、任务或项目内容输出到终端、日志或任何第三方服务。

### 附件下载原则

- 附件只下载到本地 `~/Downloads/teambition/<taskId>/` 目录（可由用户指定其他路径）
- **单文件超过 2 GB 时必须先告知大小并明确征得用户同意再下载**
- 不对下载的文件做任何二次上传、转发或加工

## 认证流程

本技能使用**两套 API**，各有独立认证：

### 1. Teambition Open API（主要）

用于查询任意任务详情、活动记录和项目列表，不受角色限制。

**所有请求经钉钉代理转发**（`$DINGTALK_PROXY_URL`），代理服务端托管 Teambition 应用凭证并签发 JWT。技能端不持有 AppId/SecretKey，也不签发 JWT。

### 2. 钉钉项目 API（补充，通过代理）

用于搜索用户自己参与的任务（按角色过滤）和获取员工信息。企业级 token 由代理管理，技能端不接触凭据。

**代理地址：** `$DINGTALK_PROXY_URL`（默认 `http://claude.server22.jz/api/dingtalk/proxy`）

**认证方式**（参考 `dingtalk-docs` 技能）：

- **proxyToken**（个人用户）：`X-Proxy-Token` + `X-User-Id`
- **robot key**（机器人用户）：`Authorization: Bearer <robot_token>`
  - robot_token 获取：`POST $DINGTALK_DOMAIN/api/v1/token`，请求体 `{"api_key": "rk-..."}`，返回 `{"token": "...", "expires_in": 3600}`

**所需钉钉权限：** `Project.Task.Read.All`、`Project.Task.Write.All`、`qyapi_project`

**所需 Teambition Open API Scope：**
- 读取：`tb-core:task:list`、`tb-core:teambition:file:get`
- 写入：`tbs-core:task:update`（更新任务）、评论发布无需额外 scope

### 凭据初始化

每次执行 API 调用时，按以下优先级获取凭据：

1. 环境变量 `$DINGTALK_PROXY_TOKEN` / `$DINGTALK_UNION_ID`（如已设置）
2. 本地文件 `~/.config/jz-dingtalk/proxy-token` + `~/.config/jz-dingtalk/user.json`

**在每个包含 API curl 调用的 Bash 块开头，执行凭据初始化：**

```bash
# 环境变量未设置时从本地文件读取（claude-code-server 文件由 start_session 预置）
[ -z "$DINGTALK_PROXY_TOKEN" ] && [ -f ~/.config/jz-dingtalk/proxy-token ] && DINGTALK_PROXY_TOKEN=$(cat ~/.config/jz-dingtalk/proxy-token)
[ -z "$DINGTALK_UNION_ID" ] && [ -f ~/.config/jz-dingtalk/user.json ] && DINGTALK_UNION_ID=$(python3 -c "import json;print(json.load(open('$HOME/.config/jz-dingtalk/user.json'))['unionId'])")
```

⚠️ 若本地文件不存在，提示用户前往 `http://claude.server22.jz/dingtalk-auth` 完成钉钉授权。

## Skill: task-engine-troubleshoot

# 任务引擎排障（web-service + async-service）

针对 **车载任务链路**：前端 / carly-web → **web-service**（必参与）↔ **async-service**（仅实际下发行为树时参与）。整机泛泛诊断请用 `robot-diagnosis`，上机只读操作用 `robot-peek` 或 `remote-hand`。

## 与其他技能的边界

| 情况 | 应使用 |
|------|--------|
| 任务链路问题（任务卡住/没执行/行为树异常等） | **本技能** |
| 整机健康巡检、多模块泛泛排查 | `robot-diagnosis` |
| 只需要上机看日志/状态，不涉及任务链路 | `robot-peek` / `remote-hand` |
| 纯导航/硬件/agent 问题（已定界排除任务引擎） | 按定界结果转相应团队 |

若用户只说"车有问题"而未提及任务，优先走 `robot-diagnosis`；用户明确指向任务行为时才用本技能。

## 必读完整手册

详细排障流程、grep 命令、接口表、场景说明均在 **`task-engine-playbook.md`**（同目录下）。使用前请先读取该文件，然后按下方步骤执行。

## 排查步骤

> **定界完成即可停止**——不必走完全部步骤。一旦把问题归到某个组件边界（修 or 交接），直接跳到第 7/8 步收口。

1. **确认版本** — 问清 ws/async 的 deb/tag/commit。若版本偏旧，先按 playbook §1.10 查上游是否已修复，有则建议升级。
2. **判断是否涉及 async** — 读 §1.2a：若步骤无 `bt` 前缀且 ws 日志无"行为树启动"字样，只查 `web-service.log`；若已定界为纯 BT 内问题，可先只查 `async-service*.log`。
3. **定界** — 按决策树（§1.3）判断问题落在哪一段（carly-web / ws / async / agent / iosys）。
4. **日志检索** — 按第四章场景执行 grep。版本一致时可按 §2.0 的文件+行号速跳源码；对不上则改关键字搜索，并记录版本偏差。
5. **线程与并发** — 若涉及 join/preempt/mutex/回调窗口等表象，读 §3.4 对齐时间线。
6. **接口与状态** — 查第三章 KV/topic 及第六章命令集。
7. **定界为外部组件** — 按 §1.8 整理交接材料（假设列表 + 接口验证 + 版本核对）。
8. **提出修复方案** — 按 §1.9：**先方案、使用者确认后再改**。代码修复须想清根因与影响。
9. **控制修复范围** — 按 §1.7：能单端解决就不双端改。

## 常见坑

| 坑 | 后果 | 对策 |
|----|------|------|
| 一上来就同时 grep `web-service.log` 和 `async-service*.log` | 浪费时间，被无关 BT 噪声带偏 | 先按 §1.2a 判断本条任务是否真动到 BT |
| 不问版本就开始翻代码 | 行号、分支对不上，结论全错 | 起手先按 §1.10 拿 deb/tag/commit，再决定看哪棵源码 |
| 「保险起见」ws 和 async 各打一块补丁 | 双端 review、回归面扩大、版本错配组合不可控 | §1.7：先定责任侧，单端最小改动收口 |
| 没确认就直接改代码、发版 | 引入二阶问题、契约破坏 | §1.9：先给方案+影响面，等使用者确认 |
| 定界已到外部组件还继续在 ws/async 里钻 | 越查越偏 | §1.8：交接清单（假设 + 接口验证 + 版本）写清楚转给对应团队 |

## Skill: device-log-analyzer

# 设备日志分析技能

分析 `/opt/jz/log/` 目录下的 jrosth*.log 和 jzhw*.log 日志文件，诊断激光雷达和深度相机问题。

## 与其他诊断技能的协作

| 场景 | 应使用 |
|------|--------|
| **本技能的定位** | 传感器（激光 / 相机）专项日志分析 |
| **上游**：robot-diagnosis → 本技能 | `robot-diagnosis` → 本技能 |
| **依赖**：本技能只分析日志，**不负责拉取日志**——内网走 `robot-peek`，客户现场走 `remote-hand` | `robot-peek` / `remote-hand` |
| **下游**：传感器数据确认正常但 scan_filter 输出异常（滤波/盲区/融合问题） | `scan-filter-diagnosis` |
| **下游**：定位结论非传感器/驱动问题（例如是任务编排或系统层）| 回退到 `robot-diagnosis` 或转 `task-engine-troubleshoot` |
| **并行**：iosys 包内（IO 板、激光、相机等）问题已涉及任务链路 | 与 `task-engine-troubleshoot` playbook §1.3 Q5 交叉看 |
| **下游**：传感器数据确认无驱动问题，但属于嵌入式硬件层故障（电机/IO/总线/电源等） | `embedded-troubleshoot` — 嵌入式硬件知识库 |

入口可以是用户直接命中（"激光雷达没数据"），也可以是 `robot-diagnosis` 巡检后路由到传感器/设备排查方向。**不要承接** "看下车有啥问题" 这种泛泛需求——先让 robot-diagnosis 收口再决定是否进本技能。

## 日志文件说明

### 主要日志（优先分析）

| 文件名 | 内容说明 |
|--------|----------|
| `jrosth.log` | 主驱动日志（1.2409之前版本） |
| `jrosth-laser2d.log` | 2D激光雷达日志（1.2409及以后） |
| `jrosth-laser3d.log` | 3D激光雷达日志 |
| `jrosth-camera.log` | 深度相机日志（1.2409及以后） |
| `iosys_iobox.log` | IO板激光日志 |
| `iosys_camera_node_{位置}.log` | JZ相机日志 |

### 备选日志（无上述文件时分析）

| 文件名 | 内容说明 |
|--------|----------|
| `jzhw_node_subp.log` | 硬件子进程日志 |
| `jzhw_node.log` | 硬件节点主日志 |
| `jzhw_node_err.log` | 错误日志 |

### 日志格式

```
# Jrosth格式
[2025-11-24 10:27:07.285] INFO/ERROR 消息 [源文件:行号] 线程名

# Jzhw格式
[2026-05-15 00:00:00.455][WARNING/ERROR][进程ID] [函数名] 消息 (源文件:行号)
```

## 分析流程

1. **定位日志**：使用 Glob 查找 jrosth*.log，无则查找 jzhw*.log
2. **识别问题**：根据错误模式判断问题类型
3. **生成报告**：时间精确到秒（YYYY-MM-DD HH:MM:SS）

## 问题类型与解决方案

### 类型1：设备断连

**特征**：`disconnect`、`timeout`、`check device cost:0 second`（重复）、`Connection activation failed`

**解决**：检查网线/电源 → ping测试 → 检查IP配置 → 重启设备 → 更换网线

### 类型2：驱动未启动

**特征**：`ros node init` 持续重复、`Failed to register publisher`、`ROS_MASTER_URI` 错误

**解决**：确认roscore运行 → 检查环境变量 → 验证launch配置 → 检查依赖

### 类型3：驱动启动但无数据

**特征**：`check device cost:0 second` 持续但无数据、`Skipped loading plugin`

**解决**：确认设备型号匹配 → 检查Topic → 测试数据流

## Skill: robot-model-config

# 机型配置 + 机型类问题诊断

帮助开发者在迦智机器人上完成机型设置、机型参数配置、机型检查，以及**从症状反向定位到机型配置根因**的问题诊断。

## 与其他诊断技能的协作

本技能在「诊断技能全景」中是**专项分析层**之一，专管机型配置侧的设置和反诊。

| 场景 | 应使用 |

| 机型配置完整性检查（"配全了吗"） → 场景五 | **本技能** |

## 前置知识

### 机型系统架构

第三代机型系统（emma）将配置数据分为 5 大类，所有属性 key 统一加前缀 `/j3/`：

| 类别 | 编号范围 | 说明 |
|------|---------|------|
| 名称属性 | 10001-19999 | 机型名字、版本等标识信息 |
| 整机属性 | 20001-29999 | 整车维度参数（架构、语言、依赖等） |
| 硬件组成 | 30001-39999 | 可选硬件设备（激光、相机、IO板、arm等） |
| 公共属性 | 100001-199999 | 多模块共享的配置项 |
| 模块属性 | 200001-299999 | 单模块自用的配置项 |

数据分四层来源，最终生效值（j3）按优先级规则合并生成：

| 层 | 来源 | 说明 |
|----|------|------|
| **j0** | 软件包内置 | `jcar3-params` deb 包提供，只读 |
| **j1** | 单机数据 | 本地写入的单机配置，可写 |
| **j2** | 动态数据 | 过程中可能被改动的数据（如标定值），可写 |
| **j3** | 最终生效值 | 由数据运行器按规则合并 j0/j1/j2 生成 |

**生效规则：** 对每个参数，依次查找 j2 → j1 → j0，取最先找到的值作为 j3。即 **j2 > j1 > j0**。

命令行中读取参数时看到的 `/j3/...` 即为最终生效值。普通修改机型参数写入 j1 层，标定等过程中可变数据写入 j2 层，j2 层的值会覆盖 j1 层同名参数。

### 参数编号与命名空间

每个参数有一个编号（如 10001、35001），同时有一个 `name` 字段，对应运行时的参数路径。例如：

- 编号 `10001` → name `robot_assembler_type` → 运行时路径 `/j3/robot_assembler_type`
- 编号 `20001` → name `env/distributed_type` → 运行时路径 `/j3/env/distributed_type`
- 编号 `35001` → name `jzhw/model/laser/<index>/name` → 运行时路径 `/j3/jzhw/model/laser/1/name`
