# 错误码分析文档规范

## 1 文档目标

文档应让首次接触该问题的 AI Agent 在读取错误码和同期日志后，能够：

1. 确认错误码含义、适用版本和所在模块；
2. 理解从业务入口到错误上报与恢复的完整流程；
3. 用正常/异常判据逐步缩小排查范围；
4. 区分症状、直接触发条件和根因；
5. 给出安全的临时处置、根因修复和可验证的闭环条件。

不要写成接口字段大全、源码逐行复述或没有判据的原因清单。

## 2 六章内容规范

### 2.1 错误结论

用一个摘要表承载：

- 错误码、稳定错误名、key；
- 中文描述、等级、所属模块；
- 直接触发条件和直接影响；
- 自动/人工恢复条件；
- 注册表来源；
- 分析基线、适用版本和不适用条件。

随后用一段“核心判断”区分：

- 该错误是什么；
- 它不是什么；
- 当前证据最深能确认到哪里。

紧接证据状态定义，确保全文中的概率表述统一。

### 2.2 错误触发的功能流程

先列进入流程的前置条件，再给一张简洁 Mermaid 流程图。流程图至少覆盖：

```text
业务入口 -> 上游输入 -> 核心检查/调用 -> 触发分支
        -> 状态置位 -> 对当前任务的影响 -> 对外上报
        -> 清除/恢复
```

补充真实符号组成的调用链，并说明：

- 同一错误的多个入口或阶段；
- 置位频率、去重、节流、重试和持久化；
- 恢复是自动清除、主动清除还是重启清除；
- 关联错误码的先后时序应如何解读。

不得为了完整而画出源码无法证明的节点。

### 2.3 结合日志选择排查方向

先给出最小日志集合和时间窗。诊断表固定使用以下列：

| 顺序 | 检查项 | 正常判据 | 异常判据 | 结论状态与下一步 |
|---:|---|---|---|---|

推荐顺序：

1. 时间、进程实例、机型和版本；
2. 错误码原始上报与直接触发日志；
3. 发生阶段和业务上下文；
4. 触发函数的直接输入；
5. 配置、开关和状态机条件；
6. 上游依赖与关联错误时序；
7. 底层实现中的具体失败分支。

表后必须有停止规则。现场命令默认只读，避免无边界的全盘搜索、大量数据采集或修改配置。每条命令应能服务于表中的某一步。

### 2.4 可能原因与解决方案

固定使用：

| 优先级 | 原因与唯一特征 | 负责链路 | 临时处置 | 根因修复 | 修复验证 |
|---|---|---|---|---|---|

原因必须可通过日志、数据或源码条件相互区分。禁止使用“模块异常”“数据有问题”这类与错误描述同义、但不可验证的原因。

临时处置优先保证安全与止损；根因修复必须落到具体数据生产者、协议、配置、状态机或算法分支；验证必须覆盖原始复现场景。

### 2.5 修复验证与证据索引

列出闭环判据、Agent 最少证据集和结构化输出契约。推荐契约：

```yaml
error_code: ""
error_name: ""
analysis_status: 待确认  # 已确认 / 高可能 / 待确认 / 已排除
applicable_version:
  primary_module: ""
  dependencies: {}
trigger_path: ""
trigger_stage: unknown
confirmed_facts: []
most_likely_cause:
  cause: ""
  confidence: low  # high / medium / low
  evidence: []
excluded_causes: []
missing_evidence: []
next_action: []
temporary_action: ""
root_fix: ""
verification:
  result: not_started  # passed / failed / not_started
  evidence: []
```

最后建立证据索引，至少包括：

- 注册表文件、sheet/条目或行；
- 错误定义；
- 置位与清除位置；
- 业务入口和影响路径；
- 上报转换；
- 版本/提交；
- 外部说明链接（若存在）。

### 2.6 Agent 自动排查 Playbook

Playbook 是文档的第六章，一个 YAML fenced code block，让 diagnosis-orchestrator 的确定性分析器可以不调模型、纯规则执行排查。本节定义其格式规范。

#### 2.6.1 设计约束

- **只读**：所有原语不修改机器人状态、不写配置、不重启服务。
- **确定性**：每一步的 `on_match` / `on_no_match` 必须互斥且完备，Agent 不会遇到未定义分支。
- **可离线降级**：标记 `online_only: true` 的步骤离线时必须跳过；须给出跳过后的下一步，不能阻塞整条链。
- **证据边界**：当前仓库没有源码的底层模块，相关步骤标记 `evidence_boundary: true`，不输出确定根因。

#### 2.6.2 执行原语

| 原语 | 用途 | 必填字段 | 在线/离线 |
|---|---|---|---|
| `grep_log` | 在模块日志中搜索正则，返回匹配行 | `module`, `pattern` | 均可 |
| `ros_topic_check` | 检查 ROS topic 是否存在且有数据 | `topic` | 仅在线 |
| `ros_service_check` | 检查 ROS service 是否可用 | `service` | 仅在线 |
| `process_check` | 检查进程是否存活 | `process_name` | 仅在线 |
| `extract_field` | 从日志行提取结构化字段值 | `source_step`（引用前置步骤）, `patterns`（字段→正则映射） | 均可 |
| `compare_values` | 比较值是否在阈值内 | `field`, 至少一个 `min`/`max`/`equals` | 均可 |
| `verify_fix` | 持续监控日志确认错误不再复现 | `grep_pattern`, `watch_duration_sec` | 均可 |

#### 2.6.3 步骤结构

```yaml
- id: <唯一ID，snake_case>
  description: "<人可读的步骤描述>"
  online_only: false        # 默认 false，true 时离线跳过
  evidence_boundary: false  # 默认 false，true 时不可输出根因
  
  checks:
    - type: <原语类型>
      # 原语参数...
      
      on_match:
        conclusion: "<命中后的结论文本>"
        priority: P1         # P1/P2/P3
        goto: <下一步骤 ID>  # 可选，跳转到指定步骤
        root_cause: "<根因>" # 可选，有确定证据时填写
        temp_fix: "<临时处置>"
        
      on_no_match:
        conclusion: "<未命中时的结论>"
        continue: true       # 继续下一个 check
        # 或者
        goto: <下一步骤 ID>
```

#### 2.6.4 从第 3 章决策表到 Playbook 的映射

```
决策表"顺序"列       → step.id
决策表"检查项"列     → step.description
决策表"正常判据"     → check.on_match
决策表"异常判据"     → check.on_no_match
决策表"结论与下一步" → conclusion + goto
停止规则             → stop_on_match / stop_on_no_match 标记
```

检查项中的 grep 命令必须转换为 `grep_log` 原语的 `pattern` 参数；ros 命令转换为对应原语；所有 `pattern` 必须是可以直接 grep 的正则，不能是"检查 XX 是否正常"这种概念性描述。

#### 2.6.5 从第 4 章原因表到 Playbook 的映射

```
原因表每一行          → playbook 末尾的一个 diagnose_* ID
"原因与唯一特征"列    → check.detection 的 grep_log pattern
"负责链路"列          → check.on_match.responsible_module
"临时处置"列          → check.on_match.temp_fix
"根因修复"列          → check.on_match.root_fix
"修复验证"列          → verify 步骤中的 verify_fix 原语
```

#### 2.6.6 最少步骤要求

每个 Playbook 至少包含：

1. **classify 步骤**：根据唯一日志特征区分触发链。如果只有一条触发链，至少有一个 check 确认入口。
2. **diagnose 步骤**：每个触发链至少一个深入排查步骤，从直接触发条件查到上游输入生产者。
3. **verify 步骤**：定义修复后的验证判据，至少包含 "grep 不再命中" 和 "等待 N 秒后仍不命中" 两项。
4. **fallback 分支**：所有已知检查项均未命中时，必须有 "扩大时间窗" 或 "标记 insufficient_data" 的兜底动作。

#### 2.6.7 质量检查

生成后对 Playbook 段执行：

```bash
# 检查所有 pattern 是否都可 grep（不能是概念性描述）
rg 'pattern:\s*".*?(检查|确认|判断|应该是|正常|异常)' <输出文档>
# 检查是否有未闭合的 goto 目标
rg 'goto:\s*(\S+)' <输出文档> | awk '{print $NF}' | sort | uniq -c
# 对照检查
rg '^  - id: ' <输出文档>
```

## 3 证据优先级

针对“本次事件为何发生”，证据强度通常为：

1. 同版本复现实验命中具体失败分支；
2. 同期原始日志/状态消息命中具体失败分支；
3. 部署版本源码及可核对的输入数据；
4. 当前分支源码；
5. 注册表描述和设计文档；
6. 错误名、经验和一般性推断。

注册表可以直接证明数值码映射，却通常不能单独证明现场根因。源码可以证明“什么条件会触发”，却不能单独证明“本次就是该条件”。务必按结论类型选择证据。

## 4 批量生成规则

- 每个错误码独立查注册表、枚举、置位和清除位置。
- 可复用公共功能流程，但必须标明每个错误的分叉点。
- 不复制未经验证的原因、命令或版本结论。
- 某错误属于缺失的外部模块时，交付证据边界和下一步取证要求，不冒充已完成。
- 汇总页只做索引；单码文档必须能独立被 Agent 使用。

## 5 验收清单

- [ ] 文件名、主标题、错误码、错误名一致。
- [ ] 数值映射有注册来源，且处理了重复/版本差异。
- [ ] 直接触发条件来自实际代码或明确标注为待确认。
- [ ] 功能流程包含前置条件、入口、置位、影响、上报和恢复。
- [ ] 日志决策表每一步都有正常/异常判据和下一步。
- [ ] 有停止规则，不要求 Agent 无条件遍历所有原因。
- [ ] 原因具有唯一特征，临时处置与根因修复分开。
- [ ] 验证覆盖错误清除、功能恢复和同场景复测。
- [ ] Agent YAML 含证据状态、缺失证据和验证结果。
- [ ] 代码证据使用路径、符号、版本；行号不是唯一定位。
- [ ] 没有把推测、错误名称或重启恢复写成确定根因。
- [ ] Markdown 标题编号连续，链接和命令可用。
- [ ] **Playbook 有 classify、diagnose、verify 三段，且至少有一个 fallback。**
- [ ] **Playbook 的每个 grep_log pattern 均为真实可 grep 的字符串或正则，不含概念性描述。**
- [ ] **Playbook 的每个 on_match / on_no_match 分支互斥且完备。**
- [ ] **online_only 原语有 skip_if_offline 行为定义。**
- [ ] **Playbook 覆盖第 3 章决策树的全部检查项和第 4 章的全部候选原因。**
